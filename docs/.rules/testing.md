# Testing Rules

Testing should stay basic, fast, and tied to the public brand website goals. Source of truth is the current code, `AGENTS.md`, `DESIGN.md`, backend public API docs, and these rules.

## Test Selection

- Astro components: test rendered content, links, conditional states, accessibility-relevant labels, and section structure when logic is non-trivial.
- API utilities: test URL construction, response typing, error mapping, and fallback behavior with mocked `fetch`.
- SEO metadata: test titles, descriptions, canonical URLs, Open Graph data, and structured data helpers when they are generated by code.
- Build behavior: keep at least one build/typecheck path in CI once package scripts exist.

## Boundaries

- Do not call the real brand backend in normal unit, component, or CI tests. Mock network responses.
- Do not add broad browser E2E coverage early. Use E2E only for a few high-value public flows once routing, content, and scripts are stable.
- Avoid snapshot-heavy tests and overbuilt fixtures. Assert user-visible output and contract behavior directly.
- Do not test Astro internals, CSS implementation details, or static copy with fragile assertions unless the copy is a contract.

## Expected Commands

Once package scripts exist, the minimum future verification commands should be:

- `npm run check` for Astro/TypeScript validation.
- `npm test` for unit/component/API utility tests.
- `npm run build` for production build and SEO/static rendering safety. When
  the build needs public brand API data, point `BRAND_API_BASE_URL` at the
  repo-owned local fixture server, not staging or production.

If scripts differ, update this file and CI together so local and CI verification stay aligned.
